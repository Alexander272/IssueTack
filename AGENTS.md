# IssueTrack

Система учёта заявок (тикетов). Frontend + Backend в одном репозитории.

## Стек

**Backend** (`backend/`): Go 1.25, Gin, Casbin (RBAC + realms), PostgreSQL (pgx), Redis, WebSocket (ws_hub), goose-миграции.

**Frontend** (`frontend/`): React 19 + Vite, MUI v9, Redux Toolkit + RTK Query, react-router v7, react-hook-form, `lucide-mui` (иконки), react-datasheet-grid, PWA.

## Запуск

- **Backend**: `cd backend && go run ./cmd/app`. Конфиг — `backend/configs/config.yaml`. Секреты — `backend/.env` (не коммитится). Миграции применяются автоматически при старте (`goose.Up`). HTTP на порту 9000.
- **Frontend**: `cd frontend && npm start`. Vite-proxy на `http://localhost:9000`. Билд: `npm run build`. Линт: `npm run lint`.
- **Миграции (вручную, из `backend/`)**: `goose -dir internal/migrate/postgres/migrations postgres "<dsn>" up/down`. Мемо по командам — `backend/notes.md`.

## Архитектура

- `backend/internal/repository/postgres/` — слой данных (SQL), структуры DTO в `backend/internal/models/`.
- `backend/internal/services/` — бизнес-логика. Внутри пакета интерфейсы сервисов (см. `services.go`, а также интерфейсы в самих файлах сервисов).
- `backend/internal/transport/http/handlers/` — HTTP-обработчики. Роуты регистрируются через `access.Reg.R(Resource).Read()/Write()/Delete()` + Casbin-мидлвар.
- `backend/internal/transport/middleware/` — проверка прав, извлечение actor/user из контекста.
- `frontend/src/features/` — фичи (tasks, groups, categories, access, auth, realms, sites, user). Внутри: `components/`, `types/` и API-слайс `<feature>ApiSlice.ts` (напр. `tasksApiSlice.ts`). `pages/` есть не у всех фич — часть страниц лежит в общем `frontend/src/pages/`.
- API-эндпоинты собраны в `frontend/src/app/api.ts`.

## Ключевые конвенции

- **Иконки**: только `lucide-mui` (MUI SvgIcon). НЕ использовать самописные `@/components/Icons/*` в новом коде. Цвет — через `sx={{ color }}` (не `fill`), размер — `sx={{ fontSize }}`. Исключение — brand-иконки (логотипы браузеров/ОС): в `lucide-mui` их нет, поэтому для них самописные иконки допустимы (`LoginsModal.tsx`).
- **Стили**: MUI `sx`, не Tailwind.
- **`FileDropZone` (`modules/attachments/`) при монтировании делает зоной drop всю страницу.** `dragenter/dragover/dragleave/drop` вешаются на `window`, а не на плашку, поэтому оверлей «Отпустите файлы для загрузки» показывается на весь экран и бросить файлы можно в любом месте окна (плашка остаётся компактной). Учитывается только перетаскивание файлов (`dataTransfer.types` содержит `Files`), глубина `dragenter/dragleave` считается счётчиком, `relatedTarget === null` (курсор покинул окно) гасит оверлей сразу. Оверлей рендерится `createPortal` в `document.body` с `pointerEvents: none` — верхний слой над MUI-диалогом, но события не перехватывает; обработку держат window-слушатели. Слушатели вешаются один раз, актуальные `files`/`onUpload`/`onChange` берутся через ref. Две точки использования не пересекаются по страницам (`Attachments` на `/tasks/:id`, форма создания — в `TaskCreateModal` из `TaskList`); если появится третья рядом с существующей, будет двойной аплоад — нужен общий менеджер. Проп `compact` рисует плитку-карточку вместо большой плашки — её использует `Attachments.tsx`, кладя последней ячейкой той же сетки (`height: '100%'` + `minHeight: 120`, растягивается под высоту карточек файлов); сетка рисуется и при нуле файлов (`files.length > 0 || showUpload`), иначе грузить было бы некуда. **Вставка из буфера (`Ctrl+V`)** обрабатывается тем же `handleFiles` через window-слушатель `paste`: текстовую вставку не перехватывает (файлов в буфере нет — событие не гасится), а опираться на `navigator.clipboard` нельзя — на LAN без TLS это не secure context, тогда как `clipboardData` в событии `paste` есть всегда.
- **Go**: следуй существующим паттернам сервисов/репозиториев; ошибки доступа — `models.ErrPermissionDenied` (код AU002).
- **Go: не длинный список позиционных аргументов.** Если функция собирает больше ~3–4 параметров (особенно с общей парой `scope, filter, from, to, limit, ...`), заводи DTO-структуру в `models` и передавай её целиком. Поля модели не дублируй: раз период уже в `StatisticsFilter.From/To`, второй раз его в сигнатуру не тащи. Пример — `models.StatisticsQuery` (`Scope`, `Filter`, `Dim`, `Limit`) для методов `StatisticsRepo`: было `GetStatisticsByDimension(ctx, scope, filter, dim, limit, from, to)`, стало `GetStatisticsByDimension(ctx, models.StatisticsQuery)`. Хелперы-мутаторы (`WithDimension`) возвращают копию.
- **Go: uuid-поля в query-фильтрах требуют опции gin `parser`.** `uuid.UUID` — это `[16]byte` (`reflect.Array`); без неё Gin на любой непустой `?assigneeId=…`/`?ownerId=…` отвечает 400 `["<uuid>"] is not valid value for uuid.UUID` (`binding/form_mapping.go` — `len(vs) != value.Len()`). Опция пишется **как часть form-тега через `=`**: `form:"ownerId,parser=encoding.TextUnmarshaler"` (не отдельным struct-тегом и не через `:`). См. `TestTicketFilter_BindUUIDParams` — регресс-зацепка для `TicketFilter`.
- **Файловая система не участвует в транзакциях.** Удалять файлы вложений можно только **после** коммита: внутри транзакции откат вернёт записи БД, но файлы уже не вернуть (`AttachmentService.DeleteByEntity` трогает только БД, очистка — `RemoveEntityDir` после коммита). Ошибка пост-коммит очистки — `Warn`-лог, а не ошибка ответа: операция уже завершена, максимум остаётся осиротевший файл под сборщик мусора. При переданной в сервис транзакции (`tx != nil`) момент коммита вызывающему неизвестен — файлы не трогать.
- **Журнал активности обязан писать `realm_id`.** `GET /activity-log` фильтрует по авторизованному реалму (`AND al.realm_id = $n`, реалм только из контекста), поэтому записи с NULL-реалмом не видит никто — вкладка «История» пустая. Заполнение централизовано в `ActivityLogService.executeCreate`: DTO без `RealmID` резолвится через `ActivityLogRepo.GetRealmByEntity` (заявки — из `tickets`, подзадачи — через `subtasks.ticket_id`) запросом **той же транзакции** (`getExec(tx)`) — так видна ещё незакоммиченная заявка из `Create`; названия таблиц/типов — через `models.EntityTypeTicket`/`EntityTypeSubtask` (не литералы). Неизвестный тип/осиротевшая сущность реалм не резолвит — запись остаётся «бесхозной», но журнал не роняет. Старые NULL-строки в БД дозаполняются руками (миграции-бэкфилла нет).
- **Значения снапшота журнала — человекочитаемые, уведомления — с id.** Снапшот (`oldMap`/`newMap`, вкладка «История») не должен показывать сырые uuid: id исполнителя/владельца/начальника/группы/площадки/категории заменяются ФИО/именем. Сборка вынесена в `services/activity_values.go`: `(*TicketService).logValues` (Update/Take/Transfer) и `(*SubtaskService).subtaskLogValues` (единственное id-поле подзадачи — исполнитель); у удаления — точечный `logUserLabel` (ключ `assignee`). Старые значения берутся из загруженной сущности (`…Short` несут `Name`/ФИО), новые — резолвятся по id из `change.NewVal` (не из DTO); `"none"` остаётся `"none"`; ФИО — «Фамилия Имя (username)» без пустых скобок (`logPersonName`). **Резолв best-effort**: нет резолвера (`users`/`sites`/`categories`/`groups` == nil), ошибка или пустой ответ — в лог уходит исходный id, операция не падает. **Ключ записи — сам тег** (`assigned`/`assign_changed`/`group_changed`/`site_changed`/`category_changed`…), поэтому фронт (вкладка «История») не меняется. Резолверы подключаются только в `services.go` (TicketDeps.Users/Sites, `NewSubtaskService(..., users, ...)`); `changes []*FieldChange` для `notifications`/MM **не трогаются** — там id (`NewVal` парсится как uuid). Старые записи в БД остаются с uuid.
- **Вкладка «История» (`modules/activity/ActivityTimeline.tsx`) — таймлайн.** Записи группируются по дню (логи приходят `created_at DESC`, пересортировки нет): sticky-подписи «Сегодня»/«Вчера»/`D MMMM YYYY`. Слева — rail-кружок с иконкой и цветом по типу изменения (`activityMeta.ts`: `FIELD_META`/`ACTION_META`/`MULTI_META`), у последней записи дня вертикальная линия не рисуется. Тело рендерится по `kind` поля: `status`/`priority` — чипы из `STATUS_MAP`/`PRIORITY_MAP` (старое → новое), `diff` — зачёркнутое старое → жирное новое, `date` — дата, `plain` — ФИО/имя (серое → жирное), `created` — тело `«заголовок»` (`log.entity`). Фраза («изменил статус») и иконка берутся по **единственному видимому** полю; если видимых полей несколько — `MULTI_META` («изменил поля») и строки с подписями (`Статус:`). Значения отсутствия (`none`, а также `<nil>`/`nil`/пустая строка из старых записей) рендерятся как «—» (`isNone`). Фильтр скрытых для безгруппового полей (`GROUPLESS_HIDDEN_FIELDS`) применяется до расчёта фразы/иконки, поэтому запись, где менялось только скрытое поле, не рисуется целиком. Ключи снапшота удаления (`title`/`status`/`priority`/`assignee`) — отдельные алиасы в `FIELD_META`, т.к. `Delete` пишет их без суффикса `_changed`.
- Планы фич лежат в `.opencode/plans/*.md`, живой список задач — в `TODO.md`.

### Списки в API: `data` всегда массив

- **Срез, уходящий в `SendData`, инициализировать: `data := []*models.X{}`, а не `var data []*models.X`.** nil-слайс маршалится как `{"data": null}`, и фронт, считающий `data` массивом, падает на пустой выборке. Заготовка пустого результата есть у `tickets`, `comments`, `subtasks`, `attachments`, `checklists` — это `if data == nil { return []*models.X{}, nil }` в конце функции; остальные репозитории инициализируют срез в декларации.
- **То же для вложенных полей списков** (`AccessFlags.AllowedStatuses`, `Role.Children`, `RoleWithPerms.Perms`): во фронте они объявлены как массивы, то есть `null` нарушает контракт типа.
- **Во фронте `x?.data` не спасает от `data: null`.** Опциональная цепочка прерывается только на первом звене: в `logs?.data.map(...)` при `data === null` выполняется `null.map`. Нужно `logs?.data?.map` либо `(x?.data ?? [])`. Ошибка выглядит как `Cannot read properties of null (reading 'map')` в минифицированном чанке и проявляется только на пустых данных — то есть на свежей установке, где таблица ещё пуста.
- Глобальную нормализацию в `fetchBaseQuery`/`transformResponse` НЕ делать: `data` бывает и одиночным объектом, где `null` легален.

## Запомненный пароль

Реализован во фронтенде: `features/auth/storage/rememberedCredentials.ts` (`localStorage`, ключ `@issueTrack/rememberedCredentials`), форма — `features/auth/components/SignInForm.tsx`.

- **Шифрования нет, есть обфускация.** Развёртывание — только LAN, TLS в стеке отсутствует (фронт отдаёт тот же бэкенд, `transport/http/handler.go:136`; cookie без `Secure`, `handlers/auth/auth.go:87`), а `crypto.subtle` существует только в secure context — там же и `subtle.digest`, поэтому проверку целостности пришлось делать обычным FNV-1a. Запись: `{ v, d, c, savedAt }`, где `d` — `base64(XOR(utf8({u,p}), pepper))` циклическим пейпером из билда, `c` — FNV-1a от исходной строки до XOR.
  - **Пейпер** (`OBFUSCATION_PEPPER`) — константа модуля. Репозиторий сейчас публичный, поэтому пейпер доступен всем, и он назван как метка формата, а не замаскирован под секрет; при закрытии репозитория его можно заменить на любой случайный — на эффективность это не влияет.
  - **Что это закрывает**: беглый взгляд в devtools/`localStorage`, наивный поиск пароля по диску (`grep`), скриншот/дамп хранилища.
  - **Чего не закрывает**: XSS на этом origin (декодируется одной строкой в консоли), вредонос и расширения с доступом к `localStorage`, целенаправленный разбор бандла. То есть ровно тот класс атак, ради которых стоило бы шифровать, — от него обфускация не спасает.
  - Если понадобится настоящая защита — это серверное «запечатывание» (stateless AES-GCM на бэкенде, в браузере непрозрачный токен с `exp`), а не клиентский WebCrypto.
- **Правила, которые обязаны сохраняться:**
  - запись **только после успешного входа** (`unwrap()`), не до запроса — иначе неверный пароль тоже останется на диске;
  - opt-in, `remember: false` — чистим хранилище сразу;
  - TTL 30 дней (`CREDENTIALS_TTL_MS`) по `savedAt`; порядок проверок при чтении: мусор JSON → форма записи → TTL/`savedAt` из будущего → декод → **`c` совпал** → непустые `u`/`p`. Любой провал — запись удаляется, наружу ничего не пробрасывается (`isStored`/`isPayload`).
  - **`c` обязателен**: без проверки целостности рассинхрон кодирования или подмена `d` подставят в поле пароля мусор, и пользователь не сможет войти. Смена формата — бамп `v` плюс правка проверки, а не молчаливая правка `obfuscate`/`deobfuscate`.
  - **только предзаполнение, автоотправки нет**;
  - пароль не должен попадать в состояние RTK Query: у мутаций `keepUnusedDataFor` не существует, состояние живёт до явного `reset()` — он вызывается в `finally` (`SignInForm`).
- **Стирание только по явному выходу** — `signOut.onQueryStarted` (`authApiSlice`). НЕ вешать на `resetStoreListener`: он реагирует на `resetUser`, который прилетает и при протухании refresh-куки (`app/apiSlice.ts:49`), т.е. стёр бы пароль ровно тогда, когда он нужен.
- Пароль не попадает в логи бэкенда: `handlers/auth/auth.go` пишет только username, `AuditLogDTO` пишет old/new по сущностям, а не тела запросов.
- Если стенд станет доступен извне LAN — вернуться к вопросу TLS и/или серверному «запечатыванию» (stateless AES-GCM на бэкенде, в браузере непрозрачный токен).

## Модель доступа к тикетам

Реализована в `backend/internal/services/ticket_access.go` (`TicketAccessChecker`, `CheckAccess`, `CheckWorkAccess`).

Порядок проверки `CheckAccess` (`CheckAccessOnTicket`):

1. Логика по атрибутам тикета (таблица ниже).
2. Если атрибуты отказали — обход у **начальника области** (`IsRealmSupervisor`: realm-wide `category:write` или `site:write`). Больше ничего доступ не даёт: Casbin `Enforce(user, realm, ticket, action)` из этой проверки убран — его результат только гейтил supervisor-обход, а `ticket:read/write` есть у рядовых пользователей.

Итого правило: **`атрибуты || IsRealmSupervisor`**. Та же формула в `CanManage`, `canChangeStatus`, `canAdministerTickets` и во фронтенде (`capabilities.isRealmAdmin`), поэтому рассинхрона «фронт показывает кнопку, бэкенд отказывает» больше нет. Web-роуты при этом дополнительно закрыты Casbin-мидлваром (`ticket:read`/`ticket:write`), то есть supervisor без coarse-прав не откроет страницу заявок, но на уровне сервиса (в т.ч. MM-бот и plugin-пути) видит всё.

- **Реалм для решения о доступе берётся только из `ticket.RealmID`** (`TicketAccessService.ticketRealm`). `CheckAccessOnTicket` намеренно **не принимает** `realm`, у `models.AccessCheckDTO` нет поля `Realm`, а у всех методов `Subtasks` нет параметра `realm` — компилятор не даёт повторно подставить клиентский домен в проверку доступа. Причина: тикеты грузятся по id без realm-фильтра (`tickets.GetByID` — `WHERE t.id = $1`), и клиентский realm-заголовок в домене Casbin позволял supervisor'у одного реалма открыть тикет другого.
- Заголовок `realm` задаёт домен только в `middleware.CheckPermissions`, и там же `checkRealmMembership` **до** `Enforce` проверяет членство в непустом realm (`ErrNotFound`/неактивное членство/не-UUID → 403). Пустой realm не проверяется: `Enforce` на нём ничего не разрешит, и это нужно маршрутам вне реалмов.

| Действие | Разрешено                                                                                          |
| -------- | -------------------------------------------------------------------------------------------------- |
| Read     | **создатель**, **исполнитель (assignee)**, **заказчик (owner)**, участник группы тикета или **менеджер группы** |
| Write    | **создатель** тикета или **менеджер группы** (создатель **без групп** — заказчик, Write не получает) |
| Delete   | только **менеджер группы** (создатель и исполнитель НЕ могут удалять)                               |

- Атрибутная матрица — это первый шаг; для **всех трёх действий** (включая Delete) поверх неё действует обход начальника области: `атрибуты || IsRealmSupervisor`. То есть supervisor может удалить чужой тикет не как менеджер его группы.
- Обхода «realm-wide `ticket:read/write` открывает чужую заявку» нет: заявитель с общими правами не выходит за пределы собственных заявок, а участник группы сохраняет доступ и без coarse-прав. Матрица закреплена в `TestTicketService_CheckAccess_AttributeMatrix`, кейсы `supervisor_no_coarse` — часть модели.
- **Заказчик (owner) — полноправный участник заявки, но только по чтению.** Чтение по владению добавлено в `checkTicketAttributes` (и для групповых, и для внегрупповых заявок), поэтому заказчик видит свою заявку в списке и в деталях. Write/Delete владение **не** даёт: иначе owner прошёл бы общие проверки и выставлял бы произвольные статусы в обход строгих переходов `ownerTransitionAllowed`. Комментарий owner'у выдаётся отдельно в `CommentService.Create` — когда `CheckWorkAccess` отказал, внешний комментарий (`!dto.IsInternal`) на активной заявке разрешается, если `ticket.Owner.ID == dto.UserID`; внутренние комментарии остаются за исполнителем/менеджером группы. «Взять в работу» заказчику недоступно: `TicketService.Take` и `AccessFlags.CanTake` гейтятся `ownerReadOnly` (`TicketAccessService`) — доступ только по владению (не автор, не исполнитель, не участник/менеджер группы, не начальник области). Заказчик, который ещё и участник группы тикета, остаётся «рабочим» и брать заявку может. Кейсы матрицы `*/owner/*` и тесты `TestTicketService_Take_OwnerOnly_Denied` / `TestTicketService_Take_OwnerAndMember_Success` это закрепляют.
- **Автор без групп — «заказчик», а не рабочий.** `TicketAccessService.IsCustomer(ctx, ticket, userID)` (`ticket_access.go`): нет ни управляемых, ни членских групп **в реалме тикета** (`GetManagedGroups`/`GetMemberGroups` от `ticket.RealmID`) и не начальник области. Такой автор **не получает Write**: `checkTicketAttributes` в обеих ветках (групповой и внегрупповой) при `action == Write` и `isCreator` спрашивает `IsCustomer` и при `true` доступ не возвращает. Производно (единая точка — Write) отсекаются `AccessFlags.CanWork`/`CanTake`, `CheckWorkAccess` (а с ним подзадачи и **внутренние** комментарии), а `Update` уходит в ветку `ownerOnly` — статусы ограничены `ownerTransitionAllowed`, но `canEditFields` (автор) сохраняется, поэтому заголовок/описание/прочие поля своей активной заявки автор правит. Отдельно проверяют заказчика `CanCreateSubtask` (false автору-без-групп) и `Take`. Вложение к своей заявке заказчику **разрешено** — отдельный `CanAttachToTicket` (work-доступ ИЛИ автор/владелец активной заявки); на него переключён ticket-путь `AttachmentService.checkEntityAccess` при `action == write`. Во фронтенде зеркало — `getHasNoGroups` (`userSlice.ts`): `InfoBar` не показывает автору меню «Изменить статус» вообще (`isStatusManager = isAssignee || isManager`; автору/владельцу остаются только решения владельца), `Comments` скрывает тумблер «Внутренний» при `!canWork`, `TaskDetail.tsx` разрешает вложения автору/владельцу. Кейсы матрицы `*/groupless_creator/*`, тесты `TestTicketAccessService_IsCustomer` / `_CanAttachToTicket` / `_CanCreateSubtask_CustomerDenied`, `TestTicketService_Take_Customer_Denied`, `TestTicketService_GetAccessFlags_Customer`.

- **`CheckWorkAccess`** = `CheckAccess(Write)` ИЛИ исполнитель тикета. Используется для: создания/изменения подзадач и вложений, комментариев; **сам по себе права на смену статуса заявки уже не даёт** — смена статуса гейтится `canChangeStatus` (см. ниже).
- **Смена статуса заявки** (`TicketService.canChangeStatus`, вызывается в `Update` и влияет на `computeAllowedStatuses`): только **автор, исполнитель, владелец, менеджер группы или админ реалма (realm supervisor)**. Политика Casbin `write` права на смену статуса не даёт — участник группы с realm-wide `ticket:write` переводить статусы не может. Исключения: закрытие/отмена (`closed`/`cancelled`) — только автор/менеджер/владелец (строгая проверка, `write`-права не спасают); терминальные `closed`/`cancelled` вообще неизменяемы.
- **Срок выполнения (dueDate)**: поставить/снять срок при создании может только **менеджер группы тикета или админ реалма** (`CanManage`; проверка после `autoAssign`). В `Update` срок проходит «тонкие права» (`ActionDueDateChanged` там нет — он сквозной) и гейтится `canEditFields` (создатель/менеджер группы/владелец-в-`open`) либо режимом `adminOnlyEdit` начальника области (см. ниже). Создатель/владелец/исполнитель на чужой заявке срок менять не могут. Во фронтенде (`InfoBar` — гейт «Установить срок», `TaskEditForm`/`AdvancedSettingsSection` — `canEditDueDate`) формула уже чем у бэкенда: `task.access?.isManager || capabilities.isRealmAdmin`, плюс активный статус.
- **Подзадачи**: роуты гейтятся только Casbin `read` тикета (`handlers/subtasks`), решения принимает сервис: **создание** (`Create`/`CreateSeveral`) — через **`CanCreateSubtask`** (создатель/исполнитель тикета, менеджер группы, админ реалма; Casbin `write` rights НЕ дают право создавать), плюс `CheckWorkAccess`-блокировка «замороженных»; **`Update`** — через `CheckWorkAccess`; правка содержимого (все поля кроме `status`) — через **`CanEditSubtask`** (автор подзадачи (`subtasks.created_by`, бэкфилл из `activity_logs`) или «управляющий» тикетом `CanManage` — менеджер группы / админ реалма); смену статуса может делать любой обладатель work-доступа. `Delete` — через `CheckWorkAccess` и `CheckAccess(Delete)`. Во фронтенде (`Subtasks`) управление по `canWork`, pencil для правки — `sub.createdBy === userId || canManage`, удаление — `canDelete`; кнопка «Добавить» (`canCreate = task.access?.isManager || task.access?.isAssignee || task.access?.isCreator || capabilities.isRealmAdmin`) и лента скрываются по этим флагам.
- **«Взять в работу»** (`TicketService.Take`, `POST /tickets/:id/take`, флаг `canTake` в `AccessFlags`): пользователь назначает себя исполнителем и переводит заявку в `in_progress`. Разрешено при read-доступе и активном статусе, если исполнителя нет совсем (любой активный статус), либо исполнитель — другой пользователь и статус `open`. Во фронтенде (`InfoBar`) кнопка «Взять в работу» показывается в этих случаях **вместо** «Изменить статус»; если забирать нельзя и у пользователя нет роли для меню статуса (не исполнитель и не менеджер/админ), у пользователя остаются только кнопки владельца либо ничего.
- **Исполнитель при создании заявки может выбрать исполнителем только себя.** В `applyExecutorCreateRestrictions` (`TicketService.Create`, ветка без coarse-прав) заказчик обязателен, группа/приоритет принудительно берутся из категории, срок отсутствует (`DueDate = nil`); `AssigneeID` из тела принимается **только равным `CreatorID`** (самоназначение — в т.ч. на чужую группу, «беру заявку на себя»), любой чужой id отбрасывается в `nil` — иначе он прошёл бы в `autoAssign` и подставился бы ответственным уже чужой группы. Если категория ведёт в собственную группу исполнителя и явного самоназначения нет — заявку назначают на него автоматически. Во фронтенде (`TaskCreateForm` → `CustomerSelectionSection`) у исполнителя чекбокс «Назначить исполнителем меня» (`assigneeId = currentUserId`); менеджер выбирает любого через `AdvancedSettingsSection`.
- `TicketService.Update`: если у пользователя только work-access, то разрешена смена только статуса (`ActionStatusChanged`, `ActionClosed`), остальные поля — запрет; сама смена статуса дополнительно требует `canChangeStatus`.
- Статусы `closed`/`cancelled` может ставить **автор, владелец (owner) или менеджер группы** (`isCreatorOrManager` + проверка владельца, строгая проверка — Casbin `write`-права не спасают).
- **Владелец (owner) и автор** без write/work-доступа могут делать в `Update` только три перехода (`ownerTransitionAllowed`): активный статус → `cancelled` (отменить заявку), `resolved` → `closed` (принять решение), `resolved` → `in_progress` (вернуть в работу). Все прочие смены статусов запрещены. Автор попадает в этот же режим через `isOwnerOrCreator` (`tickets.go`): безгрупповой автор — «заказчик» своей заявки, и он сохраняет возможность отменить её/принять решение/вернуть в работу даже если владельцем назначен другой пользователь. `computeAllowedStatuses` для `resolved` учитывает автора наравне с владельцем (`in_progress`). Во фронтенде `InfoBar` — `isOwner = owner?.id === userId || creator?.id === userId`, поэтому эти три кнопки видит и автор. Тесты `TestTicketService_Update_CustomerCreator_NotOwner_Cancel_Success` / `_ArbitraryStatus_Denied`.
- **Начальник области правит чужую заявку, кроме заголовка и описания.** Режим `adminOnlyEdit` в `TicketService.Update`: если `canEditFields` не даёт права (пользователь не создатель/менеджер группы/владелец) и пользователь — начальник области (`IsRealmSupervisor`, реалм из `ticket.RealmID`), то `adminOnlyEdit = true` — разрешены все поля **кроме `ActionTitleChanged`/`ActionDescriptionChanged`**: приоритет, категория, площадка, срок, заявитель, группа, исполнитель (смена группы/исполнителя по-прежнему только для админа реалма — тонкие права срабатывают раньше и `adminOnlyEdit` их не отменяет). Статусы супервизору и так разрешены (`canChangeStatus`). Заголовок/описание — строгий запрет, иначе супервизор мог бы затереть текст заявки; `canEditFields` на супервизора не распространяется (`isCreatorOrManager` — по атрибутам тикета). Во фронтенде: кнопка «Редактировать» в `TaskDetail` — `task.access?.canEditFields || task.access?.isAdmin`; в `TaskEditForm` поля «Заголовок»/«Описание» disabled при `!canEditFields`, а категория/площадка — общая секция `CategoryAndSiteSection` (каскад категория→группа НЕ применяется: в edit-форме группа независима).
- Во фронтенде (`InfoBar`) кнопка «Изменить статус» показывается **только исполнителю и менеджеру группы/админу реалма** (`isStatusManager = isAssignee || isManager`, без `canWrite`). Автор и владелец меню не видят, даже если автор состоит в группе: они ведут заявку решениями владельца — «Отменить заявку», «Подтвердить решение», «Вернуть в работу» (`isOwner` включает и автора). Чтобы начать вести свою заявку по статусам, автор берёт её в работу (`canTake`) и становится исполнителем — тогда меню появляется.
- **Терминальные статусы в меню — только менеджеру.** Пункты «Закрыта»/«Отменена» (`canSeeTerminalStatuses = isManager`) скрываются из меню у чистого исполнителя, которому бэкенд их всё равно не даёт выставить (`canChangeStatus` + `isCreatorOrManager`), — чтобы у него не висели серые недоступные пункты. Автор и владелец меню не видят вообще, поэтому закрывают/отменяют заявку решениями владельца. Авторские терминальные переходы (`ownerTransitionAllowed`) закрыты кнопками владельца, а не меню.
- Переход в `resolved` проставляет `resolved_at`; тикеты со статусом `resolved` автоматически закрываются через `tickets.resolved_to_closed_after` в `config.yaml` (0 — отключено). `closed_at` при `resolved` не проставляется.
- Переход в `resolved` возможен, только если нет подзадач в активном статусе (`open`/`in_progress`/`pending`/`on_hold`); подзадачи `resolved`/`closed`/`cancelled` не блокируют (`ErrSubtasksNotResolved`, подсчёт — `Subtasks.GetUnresolvedCount`).
- Статус `closed` можно поставить **только из `resolved`** (`ErrCloseRequiresResolved`); нерешённую задачу можно только отменить (`cancelled`).
- Закрытая/отменённая заявка **терминальна**: её статус изменить нельзя никому (в `Update` — `ErrTicketFrozen`; в `computeAllowedStatuses` для `closed`/`cancelled` разрешён лишь взаимообмен `closed⇄cancelled` автору/менеджеру/владельцу, исполнитель с work-доступом активные статусы не получает).
- На «замороженных» заявках (resolved/closed/cancelled) **внешние комментарии запрещены** (`CommentService.Create` → `isTicketInactive`), допустимы только внутренние — от исполнителя/менеджера группы (`CheckInternalAssigneeAccess`). Во фронтенде (`Comments`) на закрытой заявке переключатель скрыт и коммент форсится внутренним.
- **Закрепление (temporary)** нельзя оставлять на «замороженных» заявках (`TicketFavoritesService.Add` при inactive + `favoritesType=temporary` → `ErrTicketFrozen`; кнопка Pin скрыта в `Header`). **Избранное (permanent)** разрешено в любом статусе (кнопка «В избранное» всегда доступна).
- Тикеты без группы: в списке показываются только те, где пользователь создатель или исполнитель (`IncludeUngroupedAssignedTo` в `TicketFilter`).
- **«Мои задачи» (mode=assigned): resolved уходит в архив.** `TicketService.Get` выставляет `TicketFilter.ArchiveWithResolved`, а `whereBuilder.statusMode(archived, withResolved)` исключает `resolved` из активной вкладки и включает в архивную — решённые заявки исполнителя не засоряют рабочий список. Правило страницы сильнее явного фильтра, поэтому во фронтенде опции статусов зажаты под вкладку (`statusOptionsFor` + проп `statusOptions` в `TaskFilters`, `clampStatuses` чистит сохранённый в localStorage фильтр); смену бэкенд-статусов заявки это правило не затрагивает. **Страница «Избранное» живёт вне этого split'а**: звезду можно поставить на любой статус (включая закрытые), пин — только на активные, поэтому при `FavoritesByUser` репозиторий **не применяет** `statusMode` (`archived` остаётся лишь триггером пагинации permanent-вкладки), а на «Избранных» доступны все статусы, на «Закреплённых» — активные.
- **Главная страница «Заявки» показывает заявки, где пользователь автор ИЛИ заказчик.** Веб-страница (`pages/home/Home.tsx`) открывает `TaskList` с `mode='created_or_owned'` — та же выборка, что и «Мои заявки» в MM-боте (`TicketFilter.CreatedOrOwnedBy` → `whereBuilder.creatorOrOwner`). Это закрывает разрыв: заказчик видит свою заявку и в списке, а не только в деталях по прямой ссылке. Для realm supervisor (`canViewAll`) `mode` не влияет — он и так видит все доступные заявки.
- `realm` пробрасывается в сервисы подзадач/вложений (variadic `...string`), чтобы Casbin-проверка шла по правильному домену.

### Обычный пользователь без групп

«Обычный пользователь» — селектор `getHasNoGroups` (`userSlice.ts`): не начальник области, не управляет ни одной группой и не состоит ни в одной. Такому пользователю рабочие и аналитические сценарии не нужны, поэтому во фронтенде скрываются:

- **Пункты меню** «Задачи», «Статистика», «Избранное» — `Layout.tsx` (`grouplessHiddenRoutes`). Роуты при этом остаются достижимыми по URL (как и `managerOnlyRoutes`): скрыт именно пункт меню, отдельного guard'а на маршрут нет.
- **Поля «Приоритет» и «Срок»** — везде, где они показываются: колонки/карточки списка (`TaskTable`/`TaskRow`/`TaskCard`), деталь (`Meta`, `InfoBar`, `Subtasks`), вкладка «История» (`ActivityTimeline`), фильтры и группировка (`Popover`, `Chips`, `Toolbar`, `groupByOptionsFor`). Формы создания/редактирования и так gated по `getIsManager`, поэтому у безгруппового доп. полей нет.
- **Группа заявки** — `Participants.tsx`: безгрупповому не показываются бейдж «Группа» и название группы подписью под исполнителем (`task.group` ему ни о чём не говорит). В логе действий (`ActivityTimeline`) гасятся строки `group_changed`/`group_assigned`, а также `manager_changed`, `priority_changed` и `due_date_changed` (приоритет и срок безгрупповой не видит нигде — см. выше, руководитель — групповое поле); лог-вход, где **кроме** скрытых полей ничего не было, скрывается целиком (иначе осталась бы пустая плашка). В группировке «По назначению» (`getGroupValue`) неназначенные заявки не подписываются группой («👥 …» → «Без назначения») — флаг `hasNoGroups` передаётся из `TaskTableGrouped`/`TaskCardList`. Формы создания/редактирования группу не показывают: `AdvancedSettingsSection` (с селектом группы) gated по `getIsManager`, поэтому безгрупповой её и не выбирает.
- **Скрытые значения не должны «резать» список.** Сохранённые в `localStorage` фильтры/группировка по скрытым полям не мутируются в состоянии (это ловил бы `react-hooks/set-state-in-effect`), а гасятся производным `effectiveFilters = clampHiddenFields(filters)` — очищенный набор уходит и в запрос, и в UI. `clampStatuses` по вкладке работает так же, но по статусам (см. «Мои задачи»).
- В `Sidebar` перед «Выйти» добавлен `Divider`, чтобы выход был отделён от рабочих пунктов.

## Mattermost-бот (DM)

Реализован в `backend/internal/services/mattermost.go` + `mattermost_dialog.go` (сервис `MattermostService`). Мобильные клиенты MM не грузят webapp плагина, поэтому всё общение — через **нативные кнопки, диалоги и absolute-ссылки**.

- Меню из кнопок «Создать заявку»/«Мои заявки» вешается на **ответы бота** (справка на любое нераспознанное сообщение и команду «помощь»; приглашение на команду «заявка»), а не на открытие диалога — `sendMenu`/`menuButtons`.
- **«Мои заявки»** (`my_tickets`): выборка `myActiveTickets` (активные статусы + `resolved`; пользователь — автор или владелец, `Mode: created_or_owned`), разбивается на сообщения по `myTicketsChunkSize = 5` (предохранитель `myTicketsMaxCount = 200`, пауза `myTicketsPostDelay` между постами). Заголовок первого — «**Ваши активные заявки** (N):», следующих — «Заявки 6–10 из N:»; карточка несёт заголовок, **описание** заявки (`cardSummary` — переносы схлопнуты в одну строку, обрезка на 200 символов с «…»), статус/дату/площадку и действия. пусто — «У вас нет активных заявок.» Ответ приходит **отдельным постом** (не `update`), чтобы не потерять пост с меню.
- **Поиск заявки по номеру (`№N`, `№N текст`, `№N + файлы`) идёт в режиме `readable`.** `handleComment`/`handleAttachFiles`/`handleTicketCard` передают `Mode: readableMode` в `Tickets.Get`, сервис ставит `TicketFilter.ReadableBy` (`whereBuilder.readableBy`) — scope `creator_id OR owner_id OR assignee_id OR group_id IN (…)`. Без него обычный списочный scope («группы актора + внегрупповые, назначенные ему») отсекал заявителя: сгруппированную заявку создаёт рядовой пользователь (группа принудительно берётся из категории, `mattermost_dialog.go`), сам он в группу не входит — и бот отвечал «Заявка №N не найдена» на собственную заявку автора, хотя та же заявка показывалась в «Мои заявки» (`created_or_owned`). Исполнитель видел её по группе, поэтому у него номер работал. Чужие заявки в `readable` не попадают, а карточка дополнительно досматривается `ticketDetail → GetByID` и по-прежнему отдаёт «не найдена».
- **Действия владельца** — per-card кнопки (не `Links`), контекст `{action, ticket_id, status, from}`; `from` — смещение среза, в котором нажали кнопку. Правила как в плагине (`PluginGetTicket` → `CanCancel/CanConfirm/CanReopen`): `ticket_cancel` — владелец и `open → cancelled`; `ticket_confirm` — владелец и `resolved → closed`; `ticket_reopen` — владелец и `resolved → in_progress`. Владелец = `ticket.Owner != nil && ticket.Owner.ID == user.ID` (у заявок, созданных ботом, owner = создатель). Переходы гейтятся существующим `TicketService.Update`.
- **Все три действия идут через диалог подтверждения** — `cancelled`/`closed` терминальные, промах по кнопке необратим, поэтому `handleTicketStatusAction` только открывает диалог и статус не меняет: `openCancelDialog` (без полей; «Заявка №N. <заголовок>. Отменить заявку? Действие необратимо.» / «… Подтвердить решение и закрыть заявку? …», `CallbackId = ticket_cancel:<id>` / `ticket_confirm:<id>`) либо `openReopenDialog` (поле «Причина»). Текст заявки — `ticketSubject` (`GetSummary`, заголовок через `cardSummary`). Целевой статус берётся из действия (`actionTargetStatus`), **не** из `context["status"]` — контекст приходит от клиента.
- **Что происходит с сообщением списка** (`applyListEdit` + `myTicketsChunkAfterEdit`) — отмена и подтверждение решения **уводят заявку из активного списка**, поэтому карточка просто убирается из своего сообщения: срез берётся на элемент короче (`tickets[from : from+size-1]`), так что соседи остаются на местах, а лишняя карточка из следующего сообщения не подтягивается. Если карточка была единственной — сообщение **удаляется** (`Post.Delete`). Возврат в работу заявку в списке оставляет, поэтому срез перерисовывается целиком. **Заголовок всегда считается по состоянию до действия**, чтобы после удаления карточки «из N» не поехал; остальные сообщения списка до следующего «Мои заявки» остаются со старым тоталом. Откат к началу списка при исчезновении среза делать нельзя — это и был баг. Пост удаляется только когда смещение **ровно** совпало с новым концом списка (`from == len`), то есть карточка была единственной; на битом смещении (`from > len`) показываем начало списка, а не удаляем чужое сообщение.
- **`HandleInteractiveAction` → `ActionResult{Ephemeral}`** (`mattermost_dialog.go`): ответ на нажатие — только `ephemeral_text` (нажавшему; текст ошибки из `DomainError.Message()`), поля `UpdatePost`/`Post.ReplyCards` больше нет — все действия уходят в диалоги, а `update` там недоступен.
- **Сабмит диалогов** (`parseTicketActionCallback` → `handleCancelSubmission` / `handleReopenSubmission`): домен → пользователь → `changeTicketStatus` (`actionTargetStatus`) → `applyListEdit` (общий хеллер правки списка, `removed` = ушла ли заявка из активных) → пост-подтверждение в `submission.ChannelId` («Заявка отменена.» / «Заявка закрыта.» / «Заявка возвращена в работу. Причина: …»). У возврата в работу между сменой статуса и подтверждением идёт внешний комментарий «Заявка возвращена в работу: …» (порядок как в `TicketDetail.tsx`, т.к. на `resolved` внешние комментарии запрещены). Пустая причина — `models.ErrReasonRequired`. Ответ диалога не умеет обновлять посты (`SubmitDialogResponse` знает только `error`) и не несёт `post_id`, поэтому смещение и id сообщения кладутся в `State` диалога (`{"from":N,"post_id":"..."}`), а карточка правится прямым `Post.UpdateCards` (`PUT /posts/{id}/patch`) или удаляется `Post.Delete`. Хендлер сабмита (`handlers/mattermost`) на доменную ошибку отвечает `200 {"error": message}` — Mattermost держит диалог открытым и показывает текст.
- `pkg/mattermost`: `postProps`/`cardActions` вешают `Buttons`/`Links` на **свою** карточку (не склеивают в ведущий ряд), `Post.Create` строит props одним вызовом с ведущей карточкой кнопок, `OpenRequest.CallbackID`, `CreatePost` ретраит 429 (`rateLimited`/`retryAfter`).

### Заказчик в диалоге и синк пользователей Mattermost

- **Диалог создания заявки умеет выбор заказчика** (`ownerId` → `tickets.owner_id`). Поле собирает `ownerSelectElement` и показывается по **той же формуле, что и веб-форма**: менеджерам (realm supervisor или управляющие группы) и исполнителям (участники групп) — `canPickOwner`. Чистому заявителю поле не нужно, у него заказчик = он сам. Список — активные `Users.GetByMembership(realmID, MembershipCustomers)` (вне групп), подпись `Фамилия Имя (username)` — `customerLabel`. Нет активных заказчиков → поле не показывается. Список длиннее `dialogCustomersWarnThreshold` (300) пишем в лог, но не режем: у диалогов MM нет документированного предела на число опций.
- **Выбранного заказчика надо валидировать на сабмите** (`dialogOwnerID`): значение `ownerId` приходит из клиента, поэтому проверяются **оба** условия, как в `ownerSelectElement` — право выбирать заказчика у нажавшего (`canPickOwner`) и то, что заказчик — активный участник realm вне групп (`realmCustomers`). `TicketService.Create` проверяет только `OwnerID != nil` (tickets.go), членство в realm не проверяет. Любая неудача не ломает диалог: `OwnerID = nil` и заявка уходит на создателя.
- **Импорт пользователей Mattermost** — `MattermostService.SyncRealmUsers(ctx, realmID, actor, teamNames)`: сопоставляет по `mattermost_id`, затем email/username/ФИО, создаёт недостающих с `Source: mattermost` и добавляет всех в realm. Пустой `teamNames` — все пользователи сервера. Возвращает `SyncUsersResult{Created, Linked, Failed}`. Запускается из двух мест: бот-команда «синхронизировать [команды]» (`handleSync`) и веб — кнопка «Синхронизировать пользователей» в настройках realm (`POST /realms/:id/mattermost/sync`, `handlers/realms`).
- Права и активность интеграции проверяет сам `SyncRealmUsers`: только realm supervisor (`ErrPermissionDenied`), при выключенной интеграции или пустом `BotToken` — `ErrInvalidInput`. Боты и деактивированные пользователи Mattermost (`DeleteAt != 0`) пропускаются в `pkg/mattermost` (`syncFilter.skip`), который заодно **считает** пропущенных и пишет `Info`-лог `mattermost users skipped on sync` с `bots`/`deactivated` — по нему видно, что фильтр отработал. Частичные ошибки не проваливают синк, пользователи уходят в `Failed`; `Created` и `Failed` взаимоисключающие — созданный, но не добавленный в realm пользователь считается только неудачей.

### Защита Keycloak-синхронизации (`POST /users/sync`)

- `userService.Sync(ctx, actor, force)` удаляет пользователей, которых нет в группе Keycloak. `tickets.creator_id`/`owner_id` объявлены `ON DELETE CASCADE`, поэтому перед удалением среди **вычисленных** кандидатов (`toDelete`) одним запросом ищутся те, у кого есть заявки (`repository.Users.GetIDsWithTickets` — `UNION` по `creator_id`/`owner_id`); если они есть и `force=false` — `models.ErrKeycloakSyncLinkedUsers` (409, `SY001`) со списком до 10 имён, синхронизация не выполняется. Обход — `POST /users/sync?force=1` (`syncForceRequested`), во фронтенде — `ConfirmDialog` в `Users.tsx`. Список имён динамический, поэтому ошибка собирается функцией, а не sentinel-переменной.
- Глобальная проверка `source='keycloak' AND mattermost_id<>''` не подходит: после `SyncRealmUsers` сотрудник остаётся `source=keycloak` с заполненным `mattermost_id`, и такой фильтр заблокировал бы синк навсегда. Поэтому защита не по связи с Mattermost, а по факту наличия заявок, и проверяются только записи из `toDelete`.
- **`mapUsersData` обязан читать `source` в обеих ветках** сборки `UserData` (пользователь без членства в realm и пользователь, у которого членство есть). Регресс: во второй ветке `Source` не проставлялся, и все импортированные из Mattermost пользователи (они состоят хотя бы в одном realm — `SyncRealmUsers` вызывает `ensureRealmMembership`) приходили с пустым `Source`. Защита `source='mattermost'` для них не срабатывала, и Keycloak-синк удалял их вместе с заявками. Закреплено `TestMapUsersData_Source` в `internal/repository/postgres/users_test.go`.
- **Пустой `Source` — стоп-фактор для удаления** (`hasUnknownSource` в `users_sync.go`): `mapUserSource` схлопывает SQL `NULL`, пустую строку и неизвестные значения в `keycloak`, поэтому пустой `Source` на стороне сервиса означает потерянное при чтении поле, а не реальное значение. Такие пользователи не удаляются, попадают в Warn-лог `keycloak sync skipped users with unknown source` (счётчик `skipped_unknown_source` в итоговом логе). Это страховка от массового удаления, а не штатный сценарий: чинить нужно маппинг.
- `comments.user_id` объявлен **без** `ON DELETE`: удаление пользователя с комментариями роняет всю транзакцию сырой FK-ошибкой, а не доменным отказом. Отдельная задача (tombstone/`SET NULL`), гарь её не ловит.
- **Списки пользователей разделены по области.** `GET /users` (`handlers/users.getAll`) отдаёт **всех** пользователей независимо от realm (`GetAll(c, nil)`) — это глобальный список для страницы «Пользователи» и дашборда; realm-скоуп здесь не применяется, т.к. ручка закрыта `user:write`, а право выдаётся только системному администратору/root. Realm-скоуп — отдельная ручка `GET /users/by-realm` (realm обязателен, опциональный `?membership=customers|executors`). Не возвращать `RequireRealmUUID` в `getAll` и не удалять `/by-realm`: селекторы групп/задач/форм ходят именно в `by-realm`.

### Обязательный `action_id` и `title_link` (совместимость с MM)

- **У каждого `actions[]` обязан быть `id`.** Нажатие клиент отправляет как `POST /posts/{post_id}/actions/{action_id}`, роут принимает только `[A-Za-z0-9]+`, а сервер ищет действие по id в `props.attachments` поста (`Post.GetAction`) и берёт **первое** совпадение. Отсюда два правила: `id` непустой (иначе 404, а на MM ≥11.10 кнопка вообще не рисуется — транслятор вложений в `mm_blocks` выкидывает действия без `id`, и в веб-клиенте, и в мобильном) и **уникальный в пределах поста** (иначе нажатие на третьей карточке уедет с контекстом первой). `cardActions` проставляет `actionID(explicit, cardIdx, actionIdx)`: явный `InteractiveButton.ID`/`LinkAction.ID`, иначе позиционный `c<card>a<n>`; явный id чистится до `[A-Za-z0-9]`. У действий заявки id явный — `ticketActionID` (`t` + hex12 uuid + суффикс действия), чтобы он не «едет», когда карточка уезжает из списка.
- **Ссылка на заявку — это `title_link`, а не `url`.** Поля `url` у вложения нет ни в `model.MessageAttachment`, ни в клиентском `MessageAttachment`, ни в `translateAttachments` — «кликабельная целиком карточка» не работала ни в одной версии. Заголовок с `title_link` клиенты рисуют ссылкой (11.5.3 и ≥11.10 одинаково).
- Схема `mm_blocks` (`props.mm_blocks` + `props.mm_blocks_actions`) в MM ≥11.10 — будущая замена вложений; сейчас не используется: сервер 11.5.3 её не знает, а закреплённый SDK (`server/public v0.1.22`) типов не содержит. Переход возможен только с гейтом по версии сервера. Лимиты трансляции на 11.10+ — 100 блоков и 16000 символов на пост, срез из 5 карточек в них укладывается.

### Обязательный `grid-area` для `registerCustomRoute`

- **Компонент, зарегистрированный через `registerCustomRoute`, обязан сам задать `grid-area: center`.** Mattermost зону **не проставляет**: `root.tsx` передаёт её как пропс `css={{gridArea: 'center'}}`, `Pluggable` раздаёт его как `{...otherProps}`, а React на DOM-элементе такой пропс отбрасывает (это не `style`). Для MM это оформленный breaking change, в доке к `registerCustomRoute` сказано прямо: grid-area обязан задавать плагин.
- **Симптом без `grid-area` — «окно узкое + блеклое меню», а не ошибка в консоли.** Компонент попадает прямой дочеркой `.main-wrapper` (грид `"lhs center rhs"` / `min-content minmax(385px,1fr) min-content`), и авторазмещение уводит его в **первую свободную ячейку `lhs`** — колонку `min-content`, где лежит `#SidebarContainer`. Непрозрачный фон страницы перекрывает меню каналов, а сама страница сжимается в узкую колонку. `PluggableErrorBoundary` в нормальном случае рендерит `children` без обёртки, так что зона задаётся именно корневому элементу компонента.
- На узких экранах MM схлопывает `.main-wrapper` в единственную зону `main` (`max-width: 768px`), поэтому там тоже нужна явная `grid-area: main`, иначе имя зоны `center` не существует.
- Для вида «как штатный контент» повторять `#channel_view`: `border-radius: var(--radius-l)`, `box-shadow: var(--elevation-1)`. Разметка — `.it-ticket-page` (`mmPlugin/webapp/src/index.css`).

### Веб-ссылка и ссылка плагина в DM

- **Ссылки две, и они неравнозначны.** Plugin-ссылка (`pluginLink`, метка `[Открыть]`, `/plug/issuetrack/ticket/<id>`) ведёт на роут под `SourceGuard` + `PluginTokenGuard`, где Casbin-мидлвара нет, а доступ к заявке решается на уровне сервиса по атрибутам. Веб-ссылка (метка «Открыть в браузере», `{baseURL}/tasks/<id>`) ведёт на маршрут, закрытый coarse-правом `ticket:read`.
- **Правило веб-ссылки — два условия: получатель веб-пользователь И coarse-право.** Веб-ссылка показывается только если `Source != mattermost` (у пользователей, созданных из Mattermost, нет учётки Keycloak — в веб они не входят) **и** `AccessPolicies.Enforce(userID, ticket.RealmID, ticket, read)`. Домен берётся **только из `ticket.RealmID`** (не из realm-заголовка) по тем же причинам, что и в `TicketAccessChecker`. Нет права, не веб-пользователь или ошибка проверки — веб-ссылка не печатается (`Warn`/`Info`-лог), но DM всё равно доставляется: гейт относится к ссылке, а не к доставке.
- **Гейт живёт в трёх DM-путях, формула одна.** `mattermostNotifier.links` (канал уведомлений; `format`/`links` принимают `*models.UserData`, `Notify` уже грузит его), `MattermostService.showWebLink` — общий хелпер для `sendTicketCreatedDM` (DM «Заявка №N создана») и `myTicketCard` (карточки «Мои заявки»). В карточках и в «Заявка создана» при отсутствии веб-доступа вместо веб-ссылки печатается **deep-link плагина** (`pluginDeepLink`, `title_link` карточки). `MattermostDeps.Policies` — та же `AccessPolicies`, что у нотификатора.
- **`resolveOrCreateUser` обязан проставлять `Source`** в возвращаемом `UserData` (matched → Source найденного системного пользователя, новый → `UserSourceMattermost`, иначе гейт Source не сработает для только что созданных).
- **Вне гейта:** плагин-API (`mattermost_plugin.go` — `detail/result/item.Link`) не меняется; правило касается только DM бота.

### Ссылка из DM открывает заявку модалкой поверх канала, без перехода

- **Адрес ссылки прежний: `/plug/issuetrack/ticket/<uuid>`** (`registerCustomRoute('/ticket/:id', TicketDeepLinkPage)`, печатает бот — `pluginDeepLink`, `models.PluginRoutePrefix`). Командного маршрута `/{team}/issuetrack/ticket/…` нет и он не нужен.
- **Раньше страница заменяла собой весь чат, потому что иначе не вышло.** `registerCustomRoute` монтирует компонент как единственный вид в `.main-wrapper`, а модалка (`ModalController`) рендерится из `ChannelHeaderIcon` — MM монтирует `registerChannelHeaderIcon` только в видах канала, и тот возвращает `null` вне DM с ботом (`channelType === 'D'` + `context.bound`). На маршруте плагина нет ни чата, ни меню каналов, ни хоста модалки. В API плагинов MM нет «маршрута, открывающего модалку поверх канала» — маршрут всегда заменяет вид.
- **Основной путь — перехват клика, а не навигация** (`deepLink.installDeepLinkClickHandler`, вешается в `initialize`). Клик происходит в обычном MM, в DM с ботом, где смонтирован хост модалки (`ChannelHeaderIcon` ставит флаг `setModalHost(true)`): перехватчик гасит событие (`preventDefault` + `stopPropagation` — у `stopPropagation` есть смысл, не вся обработка ссылок в MM проверяет `defaultPrevented`) и отдаёт id заявки подписчикам (`subscribeOpen`), а они открывают модалку. Навигации нет вообще: ни перерисовки вида, ни перезагрузки. **Результат проверен на живом MM: модалка открывается поверх чата, интерфейс не перерисовывается.** Перехват срабатывает из закрытого состояния: при открытой модалке чат перекрыт подложкой (`.it-ticket-overlay`), поэтому нажать вторую ссылку нельзя — сначала модалку надо закрыть. Проп `initialPendingOpenId` у `ModalController` поэтому не меняется на лету, а задаётся при монтировании.
- **Что намеренно не перехватывается:** средняя кнопка, Ctrl/Shift/Alt, `target`/`download` — нативное «открыть в новой вкладке»; там MM сам уходит на `/plug/…`, и заявку показывает страница. Перехватчик срабатывает и при `!isModalHost()` — тогда клик не гасится, поведение прежнее. Ссылки остаются настоящими, а не превращаются в костыль.
- **Адрес канала строится по маркеру `/plug/issuetrack/ticket/` внутри `href`** (`matchDeepLink`) — берётся именно атрибут, а не `anchor.href`, чтобы не зависеть от того, как смонтирован MM. Установка под субпатом не мешает: маркер ищется внутри строки. Проверено харнессом на 13 кейсах (субпат, query, hash, экранированный uuid, чужой плагин, не-uuid).
- **Запасной путь — переход из `TicketDeepLinkPage`** (когда до маршрута дошли, а перехвата не случилось): id кладётся в `deepLink.setPendingTicket`, затем уход на `/{team}/channels/{id}` через `history.pushState` + синтетический `popstate`. **На живом MM это не сработало: интерфейс моргал, то есть MM перезагрузился по фолбэку `location.assign`.** MM использует react-router v5 (`Switch`/`Redirect`/`useHistory` в `team_controller.tsx`, `root.tsx`), и синтетический `popstate` он не подхватил — причину удалось выяснить только по сборке MM, которой здесь нет. Путь оставлен рабочим, но если перехват клика не устроит, чинить надо именно его, а не перехват.
- **Канал запоминает иконка в шапке** (`deepLink.rememberChannel(team, channel)` + `api.getCurrentTeamName`), и вместе с командой: текущая команда к моменту клика могла смениться, а адрес канала начинается с её имени. Хранилище — `sessionStorage`, не переменные модуля: фолбэк делает полную перезагрузку, где модульные переменные уже пусты. У заявки есть TTL 60 с (`TICKET_TTL_MS`). `takeChannel` читает и удаляет запись (одноразовость на случай повторного клика), поэтому при неудаче с адресом вызывается `restoreChannel` — иначе канал терялся бы до конца сессии и вторая ссылка открылась бы страницей.
- **Фолбэк фолбэка** (`deepLink.reloadTo`, полная перезагрузка): через 300 мс после клиентского перехода страница всё ещё смонтирована ⇒ переход не сработал ⇒ `location.assign`. Проверка «всё ещё смонтирован» (а не сравнение `pathname` — `pushState` меняет его в любом случае) — единственный надёжный признак. **Таймер нельзя гасить в cleanup самого эффекта:** он перезапускается на `setRedirecting(true)` и погасил бы таймер до срабатывания, то есть фолбэк не сработал бы никогда (ровно этот баг был в откатанном трамплине).
- **Перенос на `registerNeedsTeamRoute` + трамплин `/plug/…` откатан.** Гипотеза «на `/plug/…` панели серые, потому что `TeamController` зовёт `initializeTeam` только на `/:team`» **не подтвердилась**: командный маршрут и трамплин с `location.replace` не изменили вид панели команд и верхней панели, а добавили полную перезагрузку MM. Не повторять без новых данных.
- **Что реально показывает `#root` на `/plug/…` (проверено в консоли браузера, окно 1920px):** `.team-sidebar` — фон прозрачный, у `#global-header` `opacity: 1`, `#SidebarContainer` в DOM **отсутствует**, а `.main-wrapper` раскладывается в `0px 1849px 0px`, то есть колонка каналов (`lhs`) имеет ширину 0. Значит **никто ничего не затемняет** — «блеклое меню» в первом сообщении к подложке модалки отношения не имеет (она на странице заявки вообще не смонтирована). Списка каналов на маршруте плагина не будет: `NeedsTeamComponent` отдаётся `Switch`-у `TeamController` раньше `<ChannelController>`, а `Sidebar` живёт именно в `ChannelController`.
- **Подложка модалки затемняется** (`index.css:.it-ticket-overlay`, `rgba(0,0,0,0.5)`) — оставлено по решению: без затемнения карточка сливается с живым каналом и модалка не читается как отдельный слой. Ошисто версия «подложка гасит панели MM» была неверным выводом из первого сообщения. Крестик закрывает окно всегда; клик по подложке и Escape закрывают только когда черновик формы пуст (см. ниже), границы держит тень `.it-ticket-modal`.

### Черновик формы создания заявки

Форма создания (и в вебе `TaskCreateForm`, и в плагине `CreateTab`) пишет незавершённые данные в **`sessionStorage`** и восстанавливает их при повторном открытии — чтобы случайный клик мимо/перезагрузка не теряли заполненное. Ключ — `realm + user` (`@issueTrack/taskCreateDraft:{realmId}:{userId}` в вебе, `it-plugin-create-draft:{realmId}:{userId}` в плагине), чтобы на общем компьютере не подхватить чужой черновик; запись версионируется (`v`) и валидируется по форме, битый/чужой формат молча удаляется.

- **Закрытие по подложке/Escape гейтится «есть данные».** `ModalController` (плагин) и `TaskCreateModal` (MUI `Dialog` по `reason`) не закрывают окно, пока черновик непустой; крестик и успешное создание/очистка доступны всегда. Пустая форма (дефолтная площадка пользователя черновиком не считается) закрывается как раньше.
- **Очистка — только осознанно.** Черновик удаляется после успешного создания («Создать ещё» в плагине), а также отдельной кнопкой с подтверждением: в вебе — иконка `EraserIcon` с тултипом в шапке модалки (видна при непустом черновике, гейт — `onDirtyChange`), подтверждение через общий `ConfirmDialog`; в плагине — кнопка «Очистить» в футере (при непустом черновике), подтверждение — мини-диалог `.it-confirm`. Очистка сбрасывает поля, вложения и хранилище, оставаясь в форме. Закрытие крестиком **сохраняет** черновик.
- **Вложения (`File`) не персистятся** — их нельзя сериализовать, при восстановлении список пуст.
- **Авто-назначение в вебе (`AdvancedSettingsSection`) не должно затирать черновик.** Эффекты `autoAssign` (группа из категории, исполнитель из группы) срабатывают только при реальном изменении поля пользователем (сравнение с `useRef` prev), а не на первом рендере/загрузке списков.
- `reset()` в вебе сбрасывает к константе `EMPTY_FORM`, а не к `defaultValues`: последние могут быть восстановленным черновиком.

### Доп. поля формы создания в плагине (менеджер/исполнитель)

Условия формы создания перенесены из веба (`TaskCreateForm`) в плагин (`CreateTab`), **не** в плагин-сервер: `mmPlugin/server/plugin.go` — прозрачный прокси. Вся ролевая логика остаётся на бэкенде в `TicketService.Create` (`CanCreateTicket`/coarse-права, `applyExecutorCreateRestrictions`, `autoAssign`, dueDate-гейт `CanManage`), плагин только прокидывает поля — условия не дублируются, подмена полей через запрос ничего не даёт. Подзадачи/шаблоны в плагине не переносились (решение).

- **Роли и списки приходят в `/plugin/context`** (`PluginContextResult`: `isManager`, `memberGroupIds`, `groups` (реалма), `executors`/`customers` — участники по `GetByMembership`). Формула ролей — зеркало веба: `isManager = isRealmSupervisor || managedGroups>0`, `isExecutor = !isManager && memberGroupIds>0`. Справочники реалма (категории, площадки, группы) кэшируются per-realm (`pluginCache`, `pluginRealmData`), роли/списки — per-user, ошибки их загрузки — best-effort (`Warn`-лог): пользователь видит базовую форму, финальные права всё равно у `TicketService.Create`.
- **Секции**: исполнитель — «Заказчик» (селект + чекбокс «Назначить меня исполнителем», `assigneeId = currentUserId`); менеджер — «Расширенные настройки» (приоритет-чипы, заявитель, группа, исполнитель, `datetime-local` срок). Обычный заявитель доп. полей не видит. Менеджер в payload шлёт `priority/groupId/assigneeId/ownerId/dueDate`, исполнитель — только `ownerId`/`assigneeId`; пустой `priority`/`groupId` у менеджера = «по категории» (`PluginCreateTicket` подставляет из категории, если явного выбора нет).
- **`CreateTab` делает веб-подобное авто-назначение (`autoAssign`), но бэкенд всё равно авторитетен.** Эффекты `AdvancedSettingsSection` перенесены в плагин: смена категории подставляет группу (по `category.groupId`) и дефолтный приоритет категории (по `category.priority`), смена группы — её `defaultAssigneeId` (поэтому `PluginContextResult.Groups` несёт `DefaultAssigneeID`, см. `models.GroupShort`). Оба эффекта, как в вебе, защищены `useRef`-prev и работают только на реальном изменении поля — восстановленный черновик не затирается. Подставленные значения совпадают с теми, что `TicketService.Create` применил бы сам при пустых полях; сервер применяет ограничения (`applyExecutorCreateRestrictions`, `autoAssign`) даже при подмене полей через запрос, поэтому дублирование логики не даёт менеджеру/исполнителю лишних прав.
- Черновик плагина дополнен полями секций (`createDraft.ts`, `v=2`): `priority/groupId/assigneeId/ownerId/dueDate` — опциональные строки, старые черновики инвалидируются бампом версии.

### Вставка файлов из буфера в плагине (`Ctrl+V`)

Вложения в плагине выбираются файловым `<input type="file" multiple>` в двух местах: форма создания (`CreateTab`) и прикрепление к комментарию (`TicketDetail`). Оба поддерживают и вставку из буфера — общий хук `useClipboardFiles` (`mmPlugin/webapp/src/useClipboardFiles.ts`), который вешает на `window` слушатель `paste` и отдаёт `File[]` по тому же пути, что и кнопка выбора (`addFiles`/`addCommentFiles`: дедуп по имени/размеру в создании, лимит `MAX_PLUGIN_FILES = 10` в комментарии).

- **Опираться на `navigator.clipboard` нельзя** — на LAN без TLS это не secure context (в вебе по той же причине; см. `FileDropZone`). `clipboardData` внутри события `paste` доступен всегда, поэтому работает и на `http`.
- **Файлы проверяются по `clipboardData.files`, затем по `items`** (`kind === 'file'` → `getAsFile()`): скриншот в разных браузерах может оказаться только в `items`. Текст в буфере (в т.ч. вставка в textarea формы) не перехватывается — при отсутствии файла событие не гасится.
- **Плагин живёт внутри веб-приложения MM, поэтому вставка учитывает фокус и чужие поля.** Событие `paste` приходит тому элементу, который **в фокусе**; при открытии плагина фокус оставался в поле сообщения Mattermost за подложкой, поэтому `Ctrl+V` уходил в чат, а не в плагин. Поэтому `ModalController` при монтировании переносит фокус на модалку (`tabIndex={-1}` + `ref.focus()`, `.it-ticket-modal:focus { outline: none }`) — заодно это корректное поведение `role="dialog"`. Гард `ignorePaste`: пока открыта модалка плагина (`.it-ticket-modal` в DOM), файл из буфера всегда отдаётся плагину (фокус мог остаться в composer); «чужое» редактируемое поле вне `.it-ticket-modal`/`.it-ticket-page` не трогается только когда модалки нет — на странице по deep-link.
- **Слушатель `paste` — на `window` в capture-фазе, при обработке файла `preventDefault` + `stopImmediatePropagation`.** Модалка порталится в `document.body` (`createPortal`), то есть вне React-дерева MM, и событие всё равно доходит до composer за подложкой; `stopImmediatePropagation` в capture-фазе опережает его. Без этого файл из буфера попадает **и** в плагин, **и** в чат MM (проверено: убрав перехват, в Firefox получили вставку в оба места) — обработчик `paste` MM не сверяется с `defaultPrevented`.
- Вкладки модалки взаимоисключающие (`CreateTab` **или** `MyTicketsTab` → `TicketDetail`), поэтому двойной обработки одной вставки нет; на deep-link-странице модалки нет вовсе — хук работает на одном смонтированном компоненте.
- **Зависание Chrome при вставке файла с нашим кодом не связано.** Симптом воспроизводился и без capture-перехвата (bubble-слушатель + только `preventDefault`), срабатывал на **любом одном файле** из буфера, а снимался **только полным перезапуском Chrome** — ни обычный reload, ни жёсткий не помогали. Значит причина — состояние процесса Chrome (клипборд), а не страница и не `useClipboardFiles`. Если вернётся: не трогать хук, сперва проверить перезапуск браузера.

## Уведомления

Реализованы в `backend/internal/services/notifications.go` (`NotificationService`).

**Жизненный цикл события** (для каждого `Notify*`-метода): 1) собрать получателей + нейтральный `CreateNotificationDTO` (персональный тумблер `enabled` применяется только при авто-подписке в `autoSubscribeOnCreate`); 2) **deliver** — разослать по каналам (`channels []Notifier`, best-effort, ошибки логируются); канал возвращает признак реальной доставки; 3) **persist** — сохранить строку в БД (транзакция `repo.Create`, сбой одного не откатывает остальных, ошибки логируются) **только тем, кому доставлено хотя бы одним каналом**. Строка = фиксация доставки и дедупликация повторных прогонов (например, cron по просрочке); необслуженные (нет `mattermost_id`/неактивная интеграция/сбой) не персистятся и будут повторены на следующей попытке.

- **Каналы** — интерфейс `Notifier` (`services/channels.go`: `Name()` + `Notify(ctx, userID, dto, ticket) (delivered bool, err error)`). Сейчас один: `mattermostNotifier` (`services/mattermost_notifier.go`) — DM от бота реалма. Канал сам гейтит себя: тикет без `RealmID` / неактивная интеграция (`mmRepo.GetByRealm` → `IsActive`/`BotToken`) / отсутствие `mattermost_id` у пользователя — `delivered=false` без ошибки, причина логируется в `Info`; успешная отправка — `delivered=true` + Info-лог. Формат DM — в `format()`: «Новая задача / Задача обновлена / Задача удалена / Новый комментарий / Новое вложение / Задача просрочена» + `№N` (если `TicketNumber`) + заголовок; для `ticket.updated` добавляется сводка изменений из `Data.changes`, для `ticket.commented` — блок «Комментарий пользователя <ФИО>:\n<текст>» из `Data.comment` ({text, author}, пустой author — только текст). Ссылка «Открыть в браузере: {baseURL}/tasks/{id}» при непустом `baseURL`. Тот же блок комментария дублируется владельцу отдельным DM в `CommentService.notifyOwnerViaMattermost` (заголовок «№N: Тема» без слова «Новый комментарий»): ФИО автора — `commentAuthorLabel` (best-effort, при сбое загрузки автора фраза опускается, доставка сохраняется); оба пути покрывают любой источник комментария, т.к. все создания идут через `CommentService.Create`. Примечание: поле `data.changes` в `CreateNotificationDTO` хранится как **строка** (JSON-массив `FieldChange`), не как `[]byte` (иначе при маршалинге получится base64). Новый канал (push/email) — отдельный `Notifier` в списке `channels` при сборке в `services.go`.
- **Актор не уведомляется о собственных действиях**: `TicketCreated` (параметр `actorID`, `delete(recipients, actorID)`), `TicketUpdated` (`delete(...)` + исполнитель при смене статуса уведомляется только если он не актор), `TicketCommented`/`AttachmentAdded` (было ранее).
- **WebSocket** не является каналом уведомлений: `NotificationService` хаб не держит. `/api/ws` (`transport/ws/handler.go`) остаётся транспортной заготовкой: через него асинхронно отдаются непрочитанные при коннекте (`SendUnread`, `repo.GetUnread`+`MarkAllRead`), push-доставка в реальном времени не реализована. WebSocket-отправку из комментариев/тикетов не добавлять — уведомления идут через `channels` в Mattermost.
- Дублирующая DM-отправка владельцу заявки о комментарии живёт отдельно (`comments.go:notifyOwnerViaMattermost`) и используется для **внутренних** context-комментариев создателю; внешние комментарии теперь покрываются `TicketCommented` через канал.
